# Desktop waveform player: implementation and verification

22 October 2026. Local/uncommitted implementation requested by the maintainer. See [ADR-003](ADR-003-Desktop-Player.md) for the browser/PWA/Electron/Tauri decision. No desktop framework or dependency was introduced. One principal TypeScript UI and one platform-independent waveform engine remain; backend processes execute generation and browser native audio APIs perform playback.

## Run and use

Use the existing [development setup](Development.md): `npm ci`, then `npm run dev:backend` and `npm run dev` in separate terminals from the repository root. Open `http://127.0.0.1:5174`. The API stays on loopback port 3001; the browser proxies `/api`. The local service is not a public/mobile deployment.

1. Edit the existing sequence's frequency, duration, digital peak amplitude and waveform. Add/remove/reorder steps; choose 44.1/48 kHz and mono/identical stereo.
2. Choose **Start sequence (live)** for a paced, finite WAV stream generated by a separate backend process. Changes apply on the next start. The same planner/encoder also produces downloadable export files through Generate WAV.
3. Alternatively load a local WAV, then explicitly choose **Start loaded WAV**. Imports stay local; no audio upload. The bounded header validator accepts PCM16 mono/stereo at 44.1/48 kHz, at most 300 seconds/64 MiB, with header metadata within 128 KiB. Other codecs/rates/bit depths are explicitly unsupported.
4. Stop removes the media source and cancels pending starts/network playback. **Emergency audio mute** zeros gain, mutes/stops playback and latches; **Reset mute** leaves audio stopped and a new explicit start is required. This software control is not a physical interlock; OS/DAC buffering is outside its guarantee.
5. **Choose audio output** uses the browser's permission-based selector only where both `selectAudioOutput` and audio-context `setSinkId` exist. Otherwise use OS output settings and the displayed system-default/unknown route. No microphone permission is requested to enumerate more devices.

The 256-point SVG waveform monitor samples the native audio analyser while playing. It shows digital playback data, not a measured sound-card/DAC/electrode signal. Low digital amplitude may appear nearly flat at this display resolution. There is no FFT, browser synthesis or client WAV encoder. No automatic sound occurs on loading a file/page or resetting mute.

## Audio-output abstraction

Generation, playback and the future external hardware interface are independent capabilities, as defined in [ADR-003](ADR-003-Desktop-Player.md#independent-capabilities). Software development and tests do not depend on completing a hardware design. The existing sound-card/DAC route belongs to playback; any future hardware-specific control or protection interface remains a separate investigation.

`audio-output.ts` defines prepare/load/play/stop/mute/resetMute/chooseOutput/samples/subscribe/dispose. `browser-audio.ts` implements it using a media element, native decoding, a gain node and a bounded analyser. Future Android/iOS adapters can implement the same control/status contract without reproducing waveform mathematics or UI sequence rules. No mobile adapter is implemented here.

States are idle, ready, playing, buffering, stopped, completed, muted, interrupted and error. Device changes, a hidden page, context suspension, unexpected pause or stalled media stop output and require explicit restart. Natural end-of-file is completed, including browsers that deliver pause before ended. Stale resume/play/file-read/generation promises cannot restart audio after a later stop/mute. Default output is labelled as physically unexposed; a browser-selected device label remains unverified physical routing.

## Engine and live transport

The existing pure TypeScript planner/PCM encoder is extended with one `waveform.ts` oscillator module. Sine bytes are preserved. Square/triangle use normalized, truncated odd-harmonic series, with indices <=63 and every harmonic strictly below Nyquist. Digital amplitude is a conservative peak ceiling, not volts, RMS or a claim of ideal square edges. The [v0.4 specification](wiki/Signal-Specification.md) defines the exact extension. The engine contains no DOM, filesystem or device API.

`POST /api/v1/playback` accepts the existing sequence JSON and returns a same-origin single-use stream URL. `GET` of that URL is owner-session scoped. Admission allows eight pending starts, six starts/minute per owner/IP and 100 globally/minute; pending starts expire after 60 seconds. One live stream runs at a time, separate from the single export worker. No stream is saved as a completed export artifact. Lost sessions/reloads invalidate access; seeking/reusing a live URL is unsupported.

The API validates/adopts settings but does not synthesize. `live-process.mjs` forks `live-renderer.mjs`; the child calls the same planner/encoder as exports, emits 1,024-frame chunks with backpressure and roughly 250 ms generation lead, and exits on cancellation, parent disconnect or a 310-second deadline. Client disconnect aborts the child. Streaming/OS buffers mean this is soft real-time playback, not a sample-accurate interactive modulation or clock-calibration system. Worker startup and decoding introduce latency. A failed partial stream terminates, never becomes a downloadable “completed” artifact.

## Supported configurations and evidence boundary

| Configuration | Software behaviour | Physical status |
| --- | --- | --- |
| Desktop browser + ordinary laptop/desktop sound card | Native system-default playback path implemented; actual device identity may be hidden | No named sound card measured/calibrated |
| Desktop browser + compatible USB audio DAC selected in OS | Same default playback path; device change stops the app | No DAC/USB-cable/load combination verified |
| Browser exposing both output-selection APIs + permitted device | Feature-detected chooser/sink selection implemented and unit-tested; selected label displayed | No physical routing/output measurement or permission-picker result claimed |
| Browser missing either output-selection API | Clear unsupported feedback; OS-default route remains available | Device identity and route may be unknown |
| Browser without required native audio APIs, denied permission or unsupported decoder | Visible error, no fallback oscillator or boosted output | Unsupported until tested |
| Electron, Tauri, installed PWA, Android/iOS app | Not introduced; remain future evidence-driven choices | Not tested or supported by this increment |

Ordinary OS gain, mixer/resampler processing, notification mixing, DAC clock, AC coupling and load dependence can alter physical output. No bit-perfect/exclusive-mode or universal background-playback guarantee. Laptop sound cards need not be USB-C; USB-C remains the proposed Portable hardware requirement. No electrode driver, body-current setting, arbitrary voltage/current boost or unknown reference-device connection is included.

## Automated verification actually run

- `npm run check`: passed format/lint/strict types, **121 frontend and 186 backend tests**, both builds and frontend bundle boundary check. Current executable app modules retain 100% statements/branches/functions/lines coverage. No thresholds/exclusions were relaxed.
- `npm run verify:signals`: **64 independent WAV cases passed**, including both new shapes/rates/channel modes, low/high frequencies, 300-second maximum square/triangle exports, timing/headroom/stereo/fades and repeatability. Largest fully compared sample error was 0 PCM16 LSB. All 36 earlier sine fixture hashes match the original report. [Recorded inputs/source hashes/results](verification/desktop-player-initial.json).
- `npm run verify:desktop`: two real-process integration groups passed. They cover HTTP ownership/single-use access, progressive delivery before generation completes, invalid renderer input, sink failure, abort, deadline and recovery. Three actual HTTP WAV downloads independently pass Python header/frame/reference checks. Local artifacts/manifest are under `.openwave/desktop-verification/run-*`; no private recordings are used.
- Manual desktop in-app browser smoke: live triangle stream reached playing; emergency mute latched; a synthetic local triangle WAV loaded without autoplay, played after explicit reset/start and reached completed. The earlier square stream exposed a natural-pause completion bug; a regression test now covers its corrected handling. These are software observations, not instrumented output measurements.
- `tooling/desktop-browser-check.mjs` was run through the Codex computer-use browser connector against the running app: live playback, bounded 256-point monitor, emergency-mute/reset and natural completion passed. Run its exported `verifyDesktopBrowser(tab)` with a bound browser tab and a single-step editor fixture; it uses that connector's documented browser APIs, with no new driver dependency. It is separate from `npm run check`/CI and does not establish a cross-browser/device matrix. A first completion wait expired just before the UI completed; the check now refreshes state after actions and uses a short completion fixture with a longer bound.

Remote CI was not run or marked passed; paid CI remains deferred. No second human release reproduction or physical measurements have been performed. Real-process tests exercise the streaming boundary, not every export-worker supervisor failure or a complete automated browser matrix.

Documentation checks passed across the combined pending set: 31 Markdown files, 270 local links/anchors, source IDs, tables, fenced blocks and whitespace. The 64-case report contains exact inputs/artifact hashes, and all six recorded engine/checker source hashes match the measured files. Git whitespace checks passed. No old quality threshold was lowered; browser test fixtures are disposed between tests rather than suppressing media-environment errors.

## Short manual lab verification plan

This is the next desktop milestone: establish a laptop sound-card baseline, then repeat the same fixtures on a compatible USB-C DAC. Compare recorded results before selecting additional hardware. Any browser routing/lifecycle failures should inform a later desktop audio-layer decision. No physical output has been measured yet.

1. Identify computer/OS/browser/app/worker versions, sound card or DAC/cable, device route and all gain/enhancement settings. Use a qualified reviewer to choose a rated non-human electronic load, grounding/probing arrangement, instrument input limits and stop conditions. No body/electrode connections.
2. Independently verify the WAV bytes/checksum first. Play 10-second sine fixtures at 20, 125.5, 500, 1,000 and 10,000 Hz at both rates; record actual session/output rate where available. Capture loaded analog output with a suitable calibrated oscilloscope/audio analyser and frequency reference.
3. Record requested/measured frequency, estimator and uncertainty, loaded RMS/peak voltage, DC offset, gain settings, distortion/noise bandwidth and clipping. Do not convert software amplitude into a claimed terminal voltage. Agree physical pass/fail tolerances before rating a result; digital-file tolerances alone are not a hardware specification.
4. For square/triangle, capture the expected finite-bandwidth shape/spectrum and harmonic ratios. Intentional harmonics are not equivalent to a sine-wave THD fault. Compare against the specified truncated waveform, not an ideal infinitely sharp square.
5. Capture a multistep sequence and a maximum-duration run; inspect transitions, gaps, drift and start/stop latency. Test Stop, Emergency Mute/reset, output removal/change, page hiding and audio interruption. Measure residual buffered output/transients and confirm no automatic restart or silent route fallback is being claimed.
6. Publish raw captures, calibrated instrument/load details, settings, checksums, analysis method, uncertainty and failures. A second reviewer reproduces the results before adding any named sound-card/DAC pair to a verified physical matrix.

Open hardware questions remain voltage/current under load, output impedance, frequency response, clock drift, distortion, USB power/charging topology, isolation/fault handling and all Electro-Med output characteristics. Investigations INV-01/03/05/06 remain open. No hardware purchase or test was performed here.
